# 브레인스토밍: 위젯 글자 수 자동 집계 (파일 디스크 델타 스캔)

- 작성일: 2026-09-29
- 상태: Q1–Q5 확정 / Q6 미결 → 플랜 작성 가능
- 대상 프로젝트: `writing-tracker-widget` (KIYO 아님 — 단일 HTML 위젯 + 신규 Python 계층)

## Problem

위젯의 글자 수는 `+400 / +800 / +1000` 퀵버튼을 **수동으로 누르는** 방식이다. 글을 쓸 때마다 손을 떼어 위젯으로 이동해 버튼을 눌러야 하고, 그 사이 쓴 양은 기억으로 보정해야 한다.

요구: **PC에서(윈도우·맥) 실행되는 Python 프로그램이 프로그램 시작 시점부터 현재까지 쓴 글자 수를 집계해서 위젯에 전달**한다.

## Goal

글을 쓰는 행위만으로 위젯의 일일 글자 수가 자동 증가한다. 수동 버튼 조작은 없어도 되나, **없어지는 것이 아니다**(과거 날짜 수정·오보정 용도로 유지).

## Context

### 현재 아키텍처 (확인 완료)

단일 `index.html` (1,373줄) — 순수 HTML + CSS + 바닐라 JS. 빌드·패키지·테스트·백엔드 **없음**. 외부 의존성은 Google Fonts `DungGeunMo` 하나뿐. 노션/observatory 위젯 embed 용도로 추정.

데이터는 `localStorage`에만 존재:

| 키 | 용도 |
|---|---|
| `writingData` | `{"YYYY-MM-DD": 글자수}` — **유일한 데이터 원본** |
| `dailyGoal` / `weeklyGoal` / `monthlyGoal` | 목표 글자 수 |
| `quickButtonValues` | 퀵버튼 4개 값 |
| `selectedTheme` / `customPoint` | 테마 |
| `selectedCharacter` | 햄스터/고양이/토끼/곰 |
| `roomPath` / `calendarVisible` | 표시 설정 |

`writingData` 쓰기 지점은 **3개뿐** (grep 확인):

| 지점 | 함수 | 경로 |
|---|---|---|
| 퀵버튼 클릭 | `changeCount(amount)` | 수동 |
| 달력에서 과거 날짜 클릭 | `editDayCount(key)` | 수동 |
| 초기화 시 기본값 | `DOMContentLoaded` | `= 0` |

읽기 지점: `updateToday()` → `updateProgress()` / `updateCharacter()` / `updateStats()` / `renderCalendar()`.

### 신규 계층 (grep으로 부재 확인)

`fetch` 0건, `XMLHttpRequest` 0건, `WebSocket` 0건, `<iframe>` 0건, `localhost` 0건, `baseline` 0건, `delta` 0건, `setInterval` 0건.

→ Python 연동, 스캔, 기준점 관리, 폴링은 **전부 새로 작성**. 기존 코드와 충돌·회귀 위험 없음.

### 발견된 기존 결함 (기능 무관, 참고)

1. **`calculateStreak()` 오늘 미달성 시 streak가 0으로 끊김.** 어제까지 30일 연속 달성 중이고 오늘 2,000/4,000자라면 표시값은 `0`. 시작 오프셋 부재.
2. **단위 라벨 불일치.** 일일은 `GOAL n CHARACTERS`인데 주간/월간은 `WEEKLY WORDS` / `MONTHLY WORDS`. 그러나 실제 계산은 전부 글자 수(4,000 / 28,000=4,000×7 / 120,000=4,000×30)로 일관됨. **라벨만 잘못 붙어 있음.**
3. `.DS_Store`가 커밋되어 있고 `core.autocrlf` 미설정 + `.gitattributes` 없음 → `index.html`이 CRLF/LF 차이로 항상 dirty로 표시됨(내용은 100% 동일, 1,373줄 전부 CRLF↔LF).

## Constraints

### 하드 제약

- **원본은 위젯 `localStorage`.** Python은 델타만 전달 (Q2-B, 사용자 확정)
- **`.txt`만** 지원. `python-docx` 등 외부 패키지 설치 0건 (Q4, 사용자 확정)
- **글자 수 = 공백 포함, 줄바꿈(`\n`/`\r`) 제외** (Q5-A, 사용자 확정)
- **10초 주기 폴링** (Q3-A, 사용자 확정)
- **표준 라이브러리만** 사용 (`.txt` 전용의 직접적 결과)
- **윈도우·맥 양쪽** 지원

### 브라우저 제약 (Q3의 부수 결과)

`file://`로 연 HTML은 로컬 서버에 요청을 보낼 수 없다. → 위젯을 `http://localhost:8000`으로 열어야 한다. Python이 `index.html`을 서빙한다. 파일 자체는 여전히 HTML 한 개이므로 "단일 파일 위젯" 성질은 유지.

- → **CORS 헤더 필수**: Python이 `Access-Control-Allow-Origin: *`를 보내지 않으면 위젯의 `fetch`가 CORS로 차단된다.
- → 폴링 중 서버 죽음 시 `fetch` reject → **catch로 조용히 흡수**하고 마지막 캐시 값 유지. 안 그러면 10초마다 Promise rejection이 콘솔에 쌓인다.
- → **서버 미가동 상태 표시**를 사용자에게 보여줄지(잠재 Q)는 미결.

### 테스트 제약

폴더에 샘플 txt를 **커밋**하면 카운터가 매 실행마다 "신규 파일 = 신규 글자"로 잡는다. → **첫 실행 baseline 설계가 필수** (아래 부수 결과).

## Recommended Direction

### 데이터 흐름

```
[PC: novels 폴더의 .txt]
   │  (Python이 10초마다, 또는 위젯 폴링에 응답하며)
   ▼
[Python: 각 파일 글자수 스냅샷 → 직전 스냅샷 대비 증가분 합산]
   │  JSON: { "delta": 800 }
   ▼
[위젯: 10초마다 GET /delta → changeCount(800) → writingData 누적 → saveData() → 갱신]
```

### 위젯 → Python API (최소 1개)

| 메서드 | 경로 | 응답 | 비고 |
|---|---|---|---|
| GET | `/api/delta` | `{ "delta": int }` | 위젯이 10초마다 호출. **응답 시 그 시점까지 스캔 후 값 반환**(push 아님) |

`delta` 반환은 **상태 변경(get → 스캔·소비) 이 합계된 형태**. 위젯이 못 받아 버린 델타(탭 닫힘, 네트워크 단절)가 영구 소실되지 않게 하려면 Python이 "마지막 소비 시점"을 기억해야 하나, Q2-B 결정상 **소실은 허용**된다(Python은 델타만 전달, 원본 없음). 탭을 닫은 동안 쓴 양은 다음 실행 시 새 델타로 잡히지 않는다 → **잠재 Q**.

### 기준점(baseline) 설계 — 반드시 선결

Python은 두 가지 상태를 갖는다:

1. **파일별 글자수 스냅샷** — `{경로: 글자수}`. 직전 값 대비 증가분을 델타로.
2. **첫 실행 시** — 스냅샷이 없으면 **기준점만 설정하고 델타 0을 반환**해야 한다. (그렇지 않으면 기존 원고 전체가 "오늘 쓴 양"으로 잡힘)

스냅샷은 Python 프로세스 메모리에만 둔다(파일 저장 없음). → **재시작하면 기준점 리셋 → 다음 스캔에서 전체가 델타로 잡힘.** 이건 사용자 확정 취지("**프로그램 시작 부터 지금까지의 카운트**")와 정확히 일치하므로 **의도된 동작이며 그대로 두는 게 옳다.** 다만 이 사실을 사용자가 알고 있는지는 별개 (Q6-Q).

## Re-sequencing Impact

이 브레인스토밍은 **기존 plan 시퀀스를 재배열하지 않는다.** 선행 plan이 없는 신규 작업이며, 선행 브레인스토밍도 없다.

다만 본 작업이 확정하는 신규 제약이 **이후 작업의 순서를 바꿀 수 있다**:

- **Q2-B(원본=위젯)는 "서버 밖에서도 위젯 데이터는 살아 있다"는 전제를 못 만든다.** `localStorage`는 브라우저 프로필 종속이라 브라우저 초기화 시 전부 소실된다. 서버가 없는 상태에서도 위젯은 마지막 캐시를 보여주지만 그 데이터의 유일한 백업이 없다. → 데이터 백업/내보내기 작업이 필요하다면 **본 작업이 그 전제(서버 중심 아님)를 확정해 둔 상태에서** 설계되어야 한다.
- **Q1-C(파일 스캔)는 데이터가 "브라우저 밖(PC 파일)"에 원천적으로 묶여 있음을 확정한다.** 과거 데이터 이관을 다룰 계획이 있다면 그 계획의 전제(위젯이 단일 진실)는 이미 성립하지 않는다.
